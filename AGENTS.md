# AGENTS.md — правила для любого агента

Действуют для любого агента (Claude, Codex, Grok и другие) и не зависят от конкретного MCP или инструмента.
Где правило агента (`CLAUDE.md` и т. п.) расходится с этим файлом, главнее этот файл.

## Ветки — строгое правило

Один агент — одна постоянная ветка. Агенты никогда не делят рабочую ветку.

| Агент | Ветка | Роль |
|---|---|---|
| **Автор (человек)** | любая | Дизайн, приоритеты, последнее слово по объёму и интеграции. |
| **Claude** | `ue-claudeflow` | Технический директор: исследование, архитектура, сборка и CI, ревью. См. `CLAUDE.md`. |
| **Codex** | `ue-codex` | Геймдизайн-критика, UX/QA-ревью, реализация согласованных механик. См. `CODEX.md`. |
| **Grok** | `ue-grok` | Аудит объёма и рисков. Предлагает, сам не реализует, если автор не попросил. |

- Префикс ветки агента — `ue-`. Новую ветку агента создаёт только автор или агент по прямой просьбе автора.
- Не создавать временных веток (task, fix, experiment, research и т. п.).
- Перед первой записью проверить, что текущая ветка — своя. Если своей ветки нет или в неё нельзя писать —
  остановиться и сказать автору, а не писать в чужую ветку.
- Никогда не коммитить и не пушить в чужую ветку агента, не двигать её силой.
- `production` — согласованное состояние. Изменения в `production` только по просьбе автора.

## Движок и период (решение автора, 20.11.2026)

- **UE 5.8.4 на весь период до релиза.** Версию движка не меняет ни один агент. Для сборок на Linux —
  тулчейн clang 20.1.8 (v26), как требует Epic для 5.8.
- **До лета — только Blueprint.** C++ не добавляем: на текущем ноутбуке (4 ГБ RAM) нет места под
  Visual Studio и нет смысла в компиляции.
- **Когда появится машина мощнее** — переходим в режим Remote (агент работает прямо на машине автора)
  и переписываем на C++ то, что этого требует по конкретной причине, а не ради самого C++.
- Логика, написанная облачным агентом, передаётся **трафаретом** ([`docs/blueprints/project/`](docs/blueprints/project/README.md)),
  а не описанием словами. Зеркало `Content/` и `Config/` задаёт точные **будущие пути настоящего UE-проекта**;
  один MD = один asset либо конфигурационный файл. Текстовые файлы не заменяют `.uasset`.
- Локальный **Claude Code через реально подключённый Unreal MCP** собирает asset в открытом UE 5.8.4,
  компилирует, сохраняет, проверяет runtime/PIE, сравнивает actual с stencil и фиксирует доказательства,
  расхождения и улучшения в [`BACKLOG.md`](docs/blueprints/project/BACKLOG.md) в **своей** ветке `ue-claudeflow`.
  При недоступной MCP-операции честно ставить BLOCKED, не имитировать исполнение. Изменения stencil
  передаются Codex через handoff, а не правкой чужой ветки.

## Commit и push

- В **свою** ветку агент коммитит и пушит сам, без отдельного разрешения: локальные коммиты облачной
  сессии могут пропасть вместе с ней.
- **Только с разрешения автора:** pull request, merge в `production`, любые изменения чужих веток,
  создание новых веток.
- Никогда: `push --force`, `rebase` опубликованной ветки, переписывание истории, удаление веток.
- Репозиторий публичный. Перед push проверить, что в коммите нет секретов, личных данных и материалов,
  которые автор не готов показывать; при сомнении — спросить.

## Синхронизация перед задачей

Перед каждой новой задачей и перед первой записью в ней агент подтягивает `production` в свою ветку:

1. `git fetch origin production <своя-ветка>`.
2. `git merge-base --is-ancestor origin/production HEAD` — уже содержит?
3. Если нет: по возможности fast-forward (`git merge --ff-only origin/production`), без лишних
   merge-коммитов. Только если у ветки есть свои коммиты — обычный `merge` (не rebase).
4. Разрешить конфликты и посмотреть влитые изменения до своих правок. Не переделывать и не откатывать
   чужое решение, уже попавшее в `production`.

Поток всегда один: `production → ветка агента → работа → проверка → push в свою ветку →
PR / merge по решению автора`.

### Несколько сессий в одной ветке

Облачный и локальный экземпляры одного агента (например, Claude в облаке и Claude на машине автора) пишут в
одну ветку. Перед первой записью — `git pull` своей ветки; после работы — сразу push. Если push отклонён —
`git pull` (merge, не rebase), разобрать конфликт и push снова. Чужие коммиты в своей ветке не откатывать.

## Один владелец на файл

- У каждого файла с кодом один владелец-агент. Темы («мир», «опыт») расплывчаты и уже привели к двум
  независимым реализациям одного и того же; список владельцев ведётся по файлам (`lab/README.md`).
- Чужой файл — только на чтение. Нужна правка — пишешь владельцу, а не правишь сам.
- Владелец отдаёт наружу **контракт**: тесты, которые должны оставаться зелёными у всех. Как устроено
  внутри — его дело.
- Эксперимент не подгоняется под гипотезу. Отрицательный результат — это результат: его объясняют,
  а не переделывают, пока не подтвердится.

## Взаимодействие агентов

- Агент смотрит чужую ветку только на чтение и делает ревью по просьбе; в чужую ветку не пишет.
- Разногласия решаются письменно (запись в `CHANGELOG.md` или карточка в `docs/research/cards/`),
  а не молчаливым откатом чужой работы.
- Общие правила (этот файл) агент меняет, только явно сказав об этом автору и записав в `CHANGELOG.md`.

Строгий baseline — установленная **UE 5.8.4**. Перед каждым новым Blueprint или правкой graph/pins
открыть официальную [документацию Epic для UE 5.8](https://dev.epicgames.com/documentation/en-us/unreal-engine),
[Blueprint API](https://dev.epicgames.com/documentation/en-us/unreal-engine/BlueprintAPI),
[Blueprint Visual Scripting](https://dev.epicgames.com/documentation/en-us/unreal-engine/blueprints-visual-scripting-in-unreal-engine).
Полный набор ссылок и технология сверки — в [манифесте](docs/gameplay/SURVIVAL_MANIFEST.md).
Epic маркирует справочник UE 5.8, не отдельный hotfix 5.8.4; расхождения проверить в **самом локальном редакторе**.
Имена инструментов MCP не предполагать — сначала проверить, что они реально доступны. Возможности UE 5.9
не применять как доказательство совместимости с 5.8.4.

## Готовое раньше своего

Своё решение пишем последним, а не первым. Порядок поиска, прежде чем делать узел, систему или алгоритм:

1. **Встроенное в UE 5.8** — справочник классов и документация Epic (с `?application_version=5.8`).
2. **Образцы Epic** — Lyra, Game Animation Sample.
3. **Открытые проекты** — ALIS и другие из `docs/research/sources.md`, с проверкой лицензии.
4. **Опыт Hoarbound** — со ссылкой на коммит, PR или документ.
5. Только теперь — своё, и в карточке записано, **почему не подошло готовое**.

Глубокий поиск (пункты 2–4) нужен, когда появляется новая система, существенная зависимость, нетривиальный
алгоритм или есть риск переизобрести штатное средство. Для мелочи достаточно пункта 1: проверил штатное —
сделал — проверил результат. Изучать Lyra ради одной функции не надо.

- Решения и приёмы копим в `docs/kb/` со ссылкой на источник и версию движка. Туда попадает только
  проверенное; слухи и «все так делают» — в раздел «Не проверено», пока нет подтверждения.
- Не пересказывай по памяти то, что можно открыть в документации: открой и сошлись.
- Подсказка из форума или видео — повод проверить по документации, а не готовое решение.

## Первичный геймплейный референс — The Long Dark (решение автора, 20.11.2026)

- **The Long Dark: Survival Mode — первичный референс игровой грамматики TheLull**, а не просто одна игра в списке вдохновения. Это означает взаимосвязанные решения игрока (погода, холод, силы, время, поиск, груз, очаг, готовка, сон, укрытие, маршрут, сохранение), а не набор независимых механик.
- Общая библиотека: [обзор](docs/gameplay/reference/README.md), [core mechanics](docs/gameplay/reference/CORE_MECHANICS.md), [связи систем](docs/gameplay/reference/SYSTEM_COUPLINGS.md), [фильтр TheLull и сквозные тесты](docs/gameplay/reference/TRANSLATION_TO_THELULL.md). **До проектирования/переписывания survival-механики агент обязан прочитать относящиеся к ней разделы и её системные связи.** Это относится к Claude, Codex, Grok и другим агентам.
- В задаче/исследовательской карточке фиксировать цепочку: **как наблюдается в TLD (источник) → с чем связано → что сохраняем/изменяем для TheLull → как проверяем сквозным сценарием**. Не заменять свидетельство общим впечатлением «как в TLD».
- Статусы источников: официальное описание, свидетельство сообщества, аналитический вывод и неизвестное — разные уровни. Нельзя объявлять собственную реконструкцию точной формулой или внутренней архитектурой Hinterland. Неизвестное — отметить и проверить, а не выдумывать.
- **Собственный фильтр обязателен:** сеттинг, камера, управление, течение времени и авторские решения TheLull могут намеренно отличаться. Не копировать ассеты, тексты, UI, код, числа баланса или чужую реализацию. И не расширять объём только потому, что в TLD существует дополнительная система.
- **Приёмка механики** должна включать хотя бы одно следствие для соседней системы и воспроизводимую последовательность «намерение → действие → цена → изменённое состояние → следующий выбор». Успешный unit-тест отдельного узла ещё не доказывает цельность геймплея.
- Документация Epic, Lyra, ALIS и другие открытые проекты — **технические источники решений**; они не подменяют приоритет TLD как геймплейного референса. Hoarbound — опыт разработки и проверенные уроки, но не автоматический стандарт поведения TheLull.
- Это правило не требует исследования TLD ради каждого мелкого исправления, не затрагивающего игровое поведение.

## Три уровня проверки — называть, какой достигнут

Главный урок Hoarbound: код работает, тесты зелёные, а в игре результат неверный. Поэтому знание и работа
делятся на три уровня, и агент обязан сказать, какой достигнут, а какой остался:

1. **Подтверждено документацией** — есть ссылка на источник и версия движка.
2. **Проверено экспериментом** — воспроизводимый прогон вне игры (лаборатория, тест, скрипт).
3. **Проверено в Unreal** — поведение увидено в редакторе или в собранной игре.

Работа закрыта только после проверки заявленного поведения на доступном уровне. Пройденный unit-тест —
это уровень 2, и выдавать его за проверенную игровую механику запрещено.

## Владелец состояния — до того, как писать систему

В Hoarbound одно состояние предмета оказывалось у двух систем сразу (рука и рюкзак показывали разное).
Поэтому перед созданием системы записывается:

- где **authoritative state**, то есть единственный источник истины;
- кто имеет право его менять, а кто только читает;
- как оно восстанавливается после загрузки сохранения.

Сложную архитектуру заранее не строим. Запрещено другое: два независимых источника истины об одном.

## Оптимизация только по измерению

- Сначала **baseline**: замер до изменений, на целевом железе, а не только в редакторе.
- Узкое место определяется измерением (Unreal Insights), а не рассуждением.
- Меняем **один фактор**, повторяем замер, сравниваем.
- Меньше узлов в графе или меньше операций — **не доказательство** ускорения. Доказательство — цифры до и после.

## Тесты проверяют поведение, а не ожидаемый ответ

- Тест закрепляет контракт и наблюдаемое поведение, а не то, что должен вернуть алгоритм.
- Если после изменения механики тест упал — сначала проверь, не был ли в нём зашит устаревший вывод.
  В лаборатории так и вышло: тест требовал наличия выбора всегда, а после правила пробуждения в части
  условий остаётся один разумный вариант. Правили тест, а не механику под тест.
- Ошибка, найденная в работе, закрывается тестом, который её воспроизводит.

## Зависимости ассетов — штатными средствами

Там, где меняется загрузка, память или структура контента (но не после каждого нового Blueprint):

- **Reference Viewer** — граф ссылок, с раздельным показом жёстких и мягких (горячие клавиши H и S);
- **Size Map** — размер ассета с зависимостями, на диске и в памяти;
- **Asset Audit** — подробности по выбранным ассетам, с выгрузкой в CSV;
- **Fix Up Redirectors** — после перемещения ассетов.

Свои анализаторы не писать, пока этих средств не хватило.

## Как ведётся исследование

1. Один вопрос — одна карточка в `docs/research/cards/` по шаблону `_template.md`, не больше двух страниц.
2. Карточка закрыта, когда в ней есть решение: взять / приспособить / отказаться / отложить до пробы.
3. Одновременно в работе не больше двух карточек.
4. Утверждения о движке подкрепляются источником: документация Epic, исходный код (файл, версия),
   открытый проект. Перед карточкой проверяй свежие новости Epic, не только документацию.
5. Каждое решение помечается: «не зависит от движка» или «привязано к UE5».
6. Решения принимает автор (владелец проекта). Агент предлагает и обосновывает.

## Дисциплина документации

- Не создавать новый документ, если смысл можно добавить в существующий. Один источник правды на тему;
  остальное — ссылки.
- Краткость — требование качества: решение, ограничения, последствия. Без пересказа сессии и сырых логов.
- `CHANGELOG.md` — короткие итоги, а не дневник агента.

## Честность отчёта

- «Готово» — только когда результат проверен; чем проверен — сказать (команда, тест, скриншот).
- Не проверено или пропущено — так и написать. Не выдавать предположение за факт.
- Не называть файл «показанным», если автор не может его открыть.

## Чего не делать

- Не писать архитектурную документацию впрок, без конкретного вопроса.
- Не переносить архитектуру Hoarbound механически: только опыт, со ссылками на коммиты, PR или Miro.
- Не добавлять инфраструктуру, модули и системы, которые пока не нужны.
- Не оценивать решения по совместимости с UE6.
- Не коммитить секреты (`.env`, ключи, токены, `settings.local.json`).

## Воспроизводимость

Изменения проекта, эксперименты, тесты и сборки должны воспроизводиться сценарием в репозитории
(Python-скрипт редактора, BuildGraph, автотест), который может запустить человек, CI или другой агент.

Исследование архитектуры и разбор исходников скрипта не требуют: достаточно ссылок на источник
(файл, версия, коммит). Не создавать инструменты только ради соблюдения правила.
