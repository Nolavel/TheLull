# AGENTS.md — правила для любого агента

Действуют для любого агента (Claude, Codex, Grok и другие) и не зависят от конкретного MCP или инструмента.
Где правило агента (`CLAUDE.md` и т. п.) расходится с этим файлом, главнее этот файл.

## Ветки — строгое правило

Один агент — одна постоянная ветка. Агенты никогда не делят рабочую ветку.

| Агент | Ветка | Роль |
|---|---|---|
| **Автор (человек)** | любая | Дизайн, приоритеты, последнее слово по объёму и интеграции. |
| **Claude** | `ue-claudeflow` | Технический директор: исследование, архитектура, сборка и CI, ревью. См. `CLAUDE.md`. |
| **Codex** | `ue-codex` | Геймдизайн-критика, UX/QA-ревью, реализация согласованных механик. См. `CODEX.md`. |
| **Grok** | `ue-grok` | Аудит объёма и рисков. Предлагает, сам не реализует, если автор не попросил. |

- Префикс ветки агента — `ue-`. Новую ветку агента создаёт только автор или агент по прямой просьбе автора.
- Не создавать временных веток (task, fix, experiment, research и т. п.).
- Перед первой записью проверить, что текущая ветка — своя. Если своей ветки нет или в неё нельзя писать —
  остановиться и сказать автору, а не писать в чужую ветку.
- Никогда не коммитить и не пушить в чужую ветку агента, не двигать её силой.
- `production` — согласованное состояние. Изменения в `production` только по просьбе автора.

## Движок и период (решение автора, 20.11.2026)

- **UE 5.8.4 на весь период до релиза.** Версию движка не меняет ни один агент. Для сборок на Linux —
  тулчейн clang 20.1.8 (v26), как требует Epic для 5.8.
- **До лета — только Blueprint.** C++ не добавляем: на текущем ноутбуке (4 ГБ RAM) нет места под
  Visual Studio и нет смысла в компиляции.
- **Когда появится машина мощнее** — переходим в режим Remote (агент работает прямо на машине автора)
  и переписываем на C++ то, что этого требует по конкретной причине, а не ради самого C++.
- Логика, написанная облачным агентом, передаётся **трафаретом** (`docs/blueprints/`), а не описанием
  словами: трафарет воспроизводится в редакторе и сверяется с результатом.

## Commit и push

- В **свою** ветку агент коммитит и пушит сам, без отдельного разрешения: локальные коммиты облачной
  сессии могут пропасть вместе с ней.
- **Только с разрешения автора:** pull request, merge в `production`, любые изменения чужих веток,
  создание новых веток.
- Никогда: `push --force`, `rebase` опубликованной ветки, переписывание истории, удаление веток.
- Репозиторий публичный. Перед push проверить, что в коммите нет секретов, личных данных и материалов,
  которые автор не готов показывать; при сомнении — спросить.

## Синхронизация перед задачей

Перед каждой новой задачей и перед первой записью в ней агент подтягивает `production` в свою ветку:

1. `git fetch origin production <своя-ветка>`.
2. `git merge-base --is-ancestor origin/production HEAD` — уже содержит?
3. Если нет: по возможности fast-forward (`git merge --ff-only origin/production`), без лишних
   merge-коммитов. Только если у ветки есть свои коммиты — обычный `merge` (не rebase).
4. Разрешить конфликты и посмотреть влитые изменения до своих правок. Не переделывать и не откатывать
   чужое решение, уже попавшее в `production`.

Поток всегда один: `production → ветка агента → работа → проверка → push в свою ветку →
PR / merge по решению автора`.

### Несколько сессий в одной ветке

Облачный и локальный экземпляры одного агента (например, Claude в облаке и Claude на машине автора) пишут в
одну ветку. Перед первой записью — `git pull` своей ветки; после работы — сразу push. Если push отклонён —
`git pull` (merge, не rebase), разобрать конфликт и push снова. Чужие коммиты в своей ветке не откатывать.

## Где живёт проект

| Место | Роль | Кто пишет |
|---|---|---|
| GitHub | Согласованное состояние и обмен между агентами: `production` + ветки агентов | Агенты — свои ветки; `production` — по решению автора |
| Рабочий HDD автора (`H:\TheLull`) | Текущие локальные изменения, Unreal работает отсюда | Автор и локальные агенты |
| Google Drive `TheLull/Backups/` | Только резервные копии: независимые датированные ZIP | `tools/backup.ps1` |

- Двусторонней синхронизации Drive с рабочей папкой нет. Unreal меняет бинарные `.uasset`, а Drive не знает
  зависимостей между ними.
- Из Drive в проект ничего не перезаписывается автоматически. Восстановление — вручную, по решению автора
  (`docs/setup/LOCAL_UE.md`).
- Процедура копирования и восстановления — в `docs/setup/LOCAL_UE.md`.

## Взаимодействие агентов

- Агент смотрит чужую ветку только на чтение и делает ревью по просьбе; в чужую ветку не пишет.
- Разногласия решаются письменно (запись в `CHANGELOG.md` или карточка в `docs/research/cards/`),
  а не молчаливым откатом чужой работы.
- Общие правила (этот файл) агент меняет, только явно сказав об этом автору и записав в `CHANGELOG.md`.

## Язык

- С автором общаться по-русски. Документация и карточки — на русском.
- Названия классов, файлов, технологий и код — на английском. Комментарии в коде — на английском, коротко.

## Готовое раньше своего

Своё решение пишем последним, а не первым. Порядок поиска, прежде чем делать узел, систему или алгоритм:

1. **Встроенное в UE 5.8** — справочник классов и документация Epic (с `?application_version=5.8`).
2. **Образцы Epic** — Lyra, Game Animation Sample.
3. **Открытые проекты** — ALIS и другие из `docs/research/sources.md`, с проверкой лицензии.
4. **Опыт Hoarbound** — со ссылкой на коммит, PR или документ.
5. Только теперь — своё, и в карточке записано, **почему не подошло готовое**.

- Решения и приёмы копим в `docs/kb/` со ссылкой на источник и версию движка. Туда попадает только
  проверенное; слухи и «все так делают» — в раздел «Не проверено», пока нет подтверждения.
- Не пересказывай по памяти то, что можно открыть в документации: открой и сошлись.
- Подсказка из форума или видео — повод проверить по документации, а не готовое решение.

## Как ведётся исследование

1. Один вопрос — одна карточка в `docs/research/cards/` по шаблону `_template.md`, не больше двух страниц.
2. Карточка закрыта, когда в ней есть решение: взять / приспособить / отказаться / отложить до пробы.
3. Одновременно в работе не больше двух карточек.
4. Утверждения о движке подкрепляются источником: документация Epic, исходный код (файл, версия),
   открытый проект. Перед карточкой проверяй свежие новости Epic, не только документацию.
5. Каждое решение помечается: «не зависит от движка» или «привязано к UE5».
6. Решения принимает автор (владелец проекта). Агент предлагает и обосновывает.

## Дисциплина документации

- Не создавать новый документ, если смысл можно добавить в существующий. Один источник правды на тему;
  остальное — ссылки.
- Краткость — требование качества: решение, ограничения, последствия. Без пересказа сессии и сырых логов.
- `CHANGELOG.md` — короткие итоги, а не дневник агента.

## Честность отчёта

- «Готово» — только когда результат проверен; чем проверен — сказать (команда, тест, скриншот).
- Не проверено или пропущено — так и написать. Не выдавать предположение за факт.
- Не называть файл «показанным», если автор не может его открыть.

## Чего не делать

- Не писать архитектурную документацию впрок, без конкретного вопроса.
- Не переносить архитектуру Hoarbound механически: только опыт, со ссылками на коммиты, PR или Miro.
- Не добавлять инфраструктуру, модули и системы, которые пока не нужны.
- Не оценивать решения по совместимости с UE6.
- Не коммитить секреты (`.env`, ключи, токены, `settings.local.json`).

## Воспроизводимость

Изменения проекта, эксперименты, тесты и сборки должны воспроизводиться сценарием в репозитории
(Python-скрипт редактора, BuildGraph, автотест), который может запустить человек, CI или другой агент.

Исследование архитектуры и разбор исходников скрипта не требуют: достаточно ссылок на источник
(файл, версия, коммит). Не создавать инструменты только ради соблюдения правила.
