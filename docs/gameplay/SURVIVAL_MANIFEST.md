# TheLull — манифест сборки системного survival
**Решение автора: 21.11.2026. Статус: обязательный проектный контракт для геймплейных решений и переноса в Unreal Engine 5.8.4.**

Этот документ — не общая декларация. Перед каждой новой survival-системой и до правки её Blueprint-трафарета агент проверяет четыре обязательных пункта ниже. Результат работы — **путь игрока в игре и воспроизводимый Blueprint**, а не очередная модель, метрика или набор разрозненных фич. Правила применяются к Codex, Claude, Grok и следующим исполнителям.

## 1. Начинать с игрового core loop, а не с частной механики или AI-агента

Рабочая грамматика опирается прежде всего на **The Long Dark: Survival Mode**: ограниченное тело + изменяющийся мир + единое время + конечные возможности. Игрок сам строит намерение и несёт цену его изменения.

**Проверяемый цикл TheLull:**
```text
утро: прочесть состояние тела, погоду, запасы и доступные цели
→ выбрать собственное намерение (не приказ агента)
→ подготовиться / оставить что-то на потом
→ выйти из убежища в замёрзший Key West
→ потратить время, тепло, силы и ограниченные ресурсы на поиск/действия
→ с добычей, знанием или неудачей вернуться либо изменить маршрут
→ решить, на что потратить остаток дня (тепло, вода, ремонт, сохранение топлива)
→ пережить ночь (в том числе возможное пробуждение и новый выбор)
→ новое утро: физические и пространственные последствия сохраняются
```
Это **наш проектный loop**, выведенный из причинных связей жанра, а не объявленная точная схема или код Hinterland. Любая механика обязана влиять минимум на ещё одно звено цикла. Протестированный отдельно «метр холода» без следующего выбора игрока не принят. В перспективе — NPC и сюжет, но core не зависит от их готовности.

**Самый первый строительный инвариант:** один authoritative game clock → упорядоченная симуляция мира → тело/убежище/ресурсы → оплачиваемое действие → сохранённое последствие. Реальное течение времени и длительные действия проходят через один путь. Никакого второго времени для сна, работы, печи или погоды.

## 2. Сначала расследовать и сопоставить реальные источники

Для новой или существенно переделываемой связи записать последовательность:
1. **TLD, Survival Mode:** наблюдаемая механика и её связь с другими; источник/версия; [официальное], [сообщество], [вывод], [неизвестно] — различать.
2. **Жанр:** как ту же задачу решают другие survival-игры и почему; искать полезный паттерн, а не имитировать его целиком.
3. **Hoarbound:** что реально реализовано в GitHub `main`, что было только запланировано в Miro и что обнаружили в build/playtest. Не приравнивать код к подтверждённому UX.
4. **Key West → TheLull:** документальный факт города и отдельная гипотеза о его поведении в вымышленной зиме. Улицы, окна, веранды, старый фонд, ветер, ориентиры и 727 меняют выбор игрока; это не канадский лес, украшенный пальмами.

**Иерархия доказательств:** исходник/официальный документ → воспроизводимый опыт → вывод/предположение. Точные закрытые формулы TLD не выдумывать, баланс/ассеты/UI/тексты не копировать. Статус каждого утверждения показывать в карточке. Заимствование архитектуры Hoarbound автоматически запрещено; брать только проверяемую связь и урок.

Параллельно с Blueprint-сборкой продолжать **отдельное исследование жанра и Key West**. Исследование не блокирует уже проверенный строительный шаг и не расползается в новые D-эксперименты без конкретной игровой неопределённости.

## 3. Каждое принятое решение переводить в собираемый Blueprint-трафарет

**Один Markdown-файл — один UE-ассет.** Основная папка сборки: [`docs/blueprints/survival_f00/`](../blueprints/survival_f00/); следующие этапы получают собственные соседние папки. Имеющиеся общие правила: [`docs/blueprints/README.md`](../blueprints/README.md).

В каждом трафарете обязаны быть:
- точный `Package` и `ParentClass`, список зависимостей и конкретный порядок создания в редакторе UE 5.8.4;
- переменные с **UE-типом, единицей, default**, пометкой runtime/config/save и *единственным* authoritative writer;
- функции/события: имена входных и выходных пинов, порядок execution, branch, интерфейсы, события, прерывания и ответственность за расход ресурсов;
- кто читает состояние, что меняет соседняя система, когда оно сохраняется и как безопасно восстанавливается;
- минимальный сценарий проверки в PIE, ожидаемые наблюдаемые результаты, ошибки/негативные проверки и отметка о фактической проверке.

**Перед интеграцией:** проверить существующие `.uasset`, owner состояния, класс/путь/пины, существующие контракты и пересечение с соседними трафаретами. Если источник и реализация расходятся, записать расхождение и его причину; не менять интерфейсы тихо. Компоненты не должны независимо записывать world time. Одно полено, один предмет и одна плата временем — по одному списанию.

Статусы не смешивать: `source verified` → `stencil drafted` → `asset assembled` → `PIE tested` → `human observed`. Один лишь MD-файл не является работающим Blueprint; зеленая Python CI не подтверждает Unreal и тем более интерес игрока.

## 4. Собирать от фундамента и проверять весь цикл, включая смысл выбора

**Порядок зависимости, не очередь академических лабораторий:**
`F00 clock/steps` → `F01 climate/shelter/heat` → `F02 body` → `F03 finite items/equipment` → `F04 paid actions/cancellation` → `F05 leave/return/night` → `F06 player feedback/discovery`.
Порядок обоснован тем, что следующее звено должно иметь точный источник времени и состояния; тонкие геймплейные детали подбираются позднее.

**Первая UE-приёмка — комната 727, а не агент:** холодная комната, негерметичное окно, печь с конечным топливом и одна доска. Игроку доступны различные физические варианты: потратить время/доску на герметизацию, потратить дрова на нагрев, или оставить как есть. Каждая стратегия оставляет разные (не заранее «выгодные») последствия в часах, комнате, теле и запасах. Через ночь эти последствия сохраняются. Для F00 сначала доказать только clock и одинаковую оплату времени; **не выдавать F00 за готовую комнату/loop**.

Требования к сквозной приёмке: один и тот же clock для вылазки/работы/сна; фиксированный порядок климат→источник тепла→комната→тело→потребности; прерывание без бесплатного результата; конечность ресурсов; корректный Save/Load; сравнение при одинаковом старте; отсутствие скрытого «правильного» выбора. После этого — короткие живые тесты: интерес, считываемость причин и собственное намерение игрока не выводятся из CI.

## Рабочая проверка перед каждым новым коммитом, который касается survival

```text
[ ] Названо конкретное звено core loop и новый выбор игрока.
[ ] Проверены TLD + жанр + фактический Hoarbound + релевантный Key West;
    неизвестное/гипотеза помечены; новое решение не противоречит авторскому.
[ ] Для каждого UE-состояния один writer, известны units/readers/save/load.
[ ] Один asset = один MD-трафарет; учтены зависимости и тест в редакторе.
[ ] Сказано, что проверено на уровне источника / Python / UE / человека.
[ ] При изменении API обновлены затронутые трафареты и место интеграции.
```
